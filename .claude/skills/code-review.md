## 리뷰 우선순위

높은 순서로 확인:

1. **정확성** — 버그, 엣지 케이스, 보안 취약점
2. **설계** — 책임 분리, 인터페이스 적절성, 확장성
3. **가독성** — 이름, 구조, 복잡도
4. **스타일** — 포맷, 컨벤션 (린터로 자동화 가능한 건 코멘트 금지)

## 코멘트 작성 원칙

**코드가 아닌 코드를 비판하기**
```
✗ "이건 잘못됐어요"
✓ "이 패턴은 X 상황에서 Y 문제가 생길 수 있어요. Z 방식은 어떨까요?"
```

**제안인지 필수인지 명시하기**
- `nit:` — 사소한 스타일, 무시해도 됨
- `suggestion:` — 더 나은 방법 제안, 선택
- `[required]` — 머지 전 반드시 수정

**이유 설명하기**
```
✗ "여기 useMemo 써야 해요"
✓ "이 계산이 렌더마다 반복되는데, useMemo로 감싸면 product 변경 시에만 재계산돼요"
```

## 머지 기준

- 지적 사항이 0개여야 머지하는 건 아님
- `nit` 수준은 해결 없이 머지 가능
- 핵심 로직 변경은 최소 1인 승인

## 리뷰 범위

- PR 크기가 크면 먼저 작게 나눠달라고 요청
- 리뷰 범위 외 발견한 문제는 별도 이슈로 분리

## 작성자 가이드

- PR 설명에 변경 이유와 테스트 방법 명시
- 리뷰어가 맥락 파악에 드는 시간을 줄여줄 것
- 스스로 리뷰해보고 올리기 (self-review)
- 코멘트 받으면 방어적으로 반응하지 말고, 모르겠으면 질문

## 리뷰 시간

- 24시간 이내 1차 응답 (팀 내 합의)
- 긴 PR은 나눠서 리뷰 가능 (`partial review` 명시)
