$ARGUMENTS 코드베이스에서 아키텍처 개선 기회를 탐색하고 "깊이 있는 모듈"로 발전시킬 후보를 제안해.

## 핵심 개념

**깊은 모듈(Deep Module)**: 작은 인터페이스 뒤에 많은 동작이 숨겨진 것. 레버리지가 높다.
**얕은 모듈(Shallow Module)**: 인터페이스가 구현만큼이나 복잡한 것. 레버리지가 낮다.

목표: 얕은 모듈을 더 깊게 만드는 **심화 기회(deepening opportunity)**를 찾는 것.

## 탐색 과정

### 1단계 — 도메인 이해
먼저 읽어야 할 것:
- `CONTEXT.md` (있는 경우) — 도메인 용어 파악
- `docs/adr/` (있는 경우) — 기존 아키텍처 결정 확인
- 그 다음 코드베이스를 유기적으로 탐색

### 2단계 — 마찰 지점 찾기
주목할 패턴:
- 많은 작은 모듈에 흩어진 개념
- 구현만큼 복잡한 인터페이스
- 테스트하기 어려운 로직
- 강하게 결합된 모듈
- **삭제 테스트**: 이 모듈을 삭제하면 복잡성이 여러 호출자로 퍼지는가? → 가치를 증명함

### 3단계 — 후보 제안

각 후보에 포함:
- 관련 파일 목록
- 현재 마찰 설명 (도메인 언어로)
- 평범한 언어로 설명한 해결책
- 로컬리티와 레버리지 관점의 이점

**인터페이스 설계는 아직 제안하지 않는다.** 먼저 후보를 검토한다.

### 4단계 — 선택된 후보 심층 논의
선택 후:
- 의존성 분류: 인-프로세스 / 로컬 대체 가능 / 원격이지만 소유 / 외부
- 인터페이스 대안 설계 (최소 2가지)
- 트레이드오프 비교

## ADR 작성 기준

다음 3가지 모두 해당할 때만 ADR 작성:
1. 되돌리기 어렵다
2. 맥락 없이는 의문을 유발한다
3. 실제 트레이드오프의 결과다
