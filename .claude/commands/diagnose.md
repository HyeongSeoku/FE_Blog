$ARGUMENTS 버그나 성능 문제를 6단계 구조화 방법론으로 진단해.

## 핵심 철학

**피드백 루프를 먼저 만들어라. 이것이 핵심 스킬이다.**

빠르고 결정론적인 테스트 신호를 먼저 확보한다. 그게 되면 근본 원인 찾기는 기계적 작업이 된다.

## 6단계 진단 과정

### 1단계 — 피드백 루프 구축
재현 가능한 테스트 신호를 만든다. 우선순위 순서:
1. 실패하는 자동화 테스트
2. HTTP 스크립트 / CLI 호출
3. 최소 재현 코드 조각
4. 브라우저 자동화

루프 자체를 속도와 결정론을 위해 최적화한다.

### 2단계 — 재현
루프를 실행하고 확인:
- 실패가 보고된 것과 일치하는가
- 안정적으로 재현되는가
- 정확한 증상을 포착했는가

### 3단계 — 가설 수립
테스트하기 전에 3~5개의 반증 가능한 가설을 순위와 함께 정리한다.
각 가설 형식: "X가 원인이라면, Y를 변경하면 사라질 것이다."

### 4단계 — 계측
디버거와 타깃 로깅으로 한 번에 하나의 변수를 테스트한다.
- 각 로그에 고유 접두사 붙이기 (나중에 제거 용이하도록)
- 예측과 대조하며 가설 기각/채택

### 5단계 — 수정 + 회귀 테스트
수정 전에:
- 올바른 아키텍처 경계에 회귀 테스트 작성
- 테스트가 실제 버그 패턴을 검증하는지 확인

그 다음 최소한의 수정 적용.

### 6단계 — 정리
- 계측 코드 (로그, 임시 플래그) 제거
- 원래 시나리오가 더 이상 재현되지 않는지 확인
- 아키텍처 개선이 필요하면 별도 이슈로 등록

## 출력 형식

```
{재현 방법}

### 검증된 가설
{원인: 왜 이것이 맞는가}

### 수정 내용
{변경 사항}

### 회귀 테스트
{추가된 테스트}
```
