$ARGUMENTS 계획을 `CONTEXT.md`와 ADR에 대조해 검증하고, 용어 불일치와 설계 충돌을 찾아내.

## 목적

도메인 모델과 기존 결정에 맞서 계획을 스트레스 테스트한다.
문서에 정의된 언어와 어긋나는 용어나 접근법을 즉시 잡아낸다.

## 방식

**한 번에 하나씩** 질문한다. 답변을 기다린 뒤 다음으로 넘어간다.

### 찾아야 할 것

**용어 불일치 지적**:
```
"문서에서는 X를 이렇게 정의하는데, 당신은 다른 의미로 쓰고 있는 것 같습니다.
 어느 쪽 의미인가요?"
```

**구체적 시나리오로 테스트**:
엣지 케이스를 발명해 개념들 사이의 관계를 강제로 명확하게 만든다.

**코드와 교차 검증**:
설명한 접근법이 실제 코드베이스와 모순되면 즉시 노출시킨다.

**결정이 굳어지면 즉시 포착**:
`CONTEXT.md` 를 배치 처리하지 않고 용어가 해소되는 즉시 업데이트한다.

### 참조 파일

- `CONTEXT.md` — 도메인 용어 정의
- `docs/adr/` — 기존 아키텍처 결정

이 파일들이 없으면 먼저 생성할 것을 제안한다.

## ADR 작성 기준

다음 3가지 모두 해당할 때만 ADR로 기록:
1. 되돌리기 어렵다
2. 맥락 없이는 의문을 유발한다
3. 실제 트레이드오프의 결과다

그 외에는 건너뛴다.

## 사용 예시

```
/grill-with-docs 캐시 레이어를 Redis로 교체하는 계획
/grill-with-docs [설계 문서 붙여넣기]
```
